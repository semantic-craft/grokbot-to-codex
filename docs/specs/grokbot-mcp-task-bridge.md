# GrokBot 插件与 Codex 任务桥：派活、结果查询及通知扩展

日期：2026-10-07。基线：`ddf2d3f`。
状态：用户已确认测试边界与工单拆分；已发布为 [GitHub #1](https://github.com/semantic-craft/grokbot-to-codex/issues/1)。实施工单见 [工单索引](grokbot-mcp-tickets.md)。
工单标签：`ready-for-agent`（已应用；阻塞关系与条件另行约束领取）。

## Problem Statement

用户希望在 GrokBot 中自然语言派活给本机 Codex，并取得真实进度、结果，必要时在官方 Codex Desktop 打开同一会话继续工作。当前已通过本地 CLI 派活测试，但每次仍需让 GrokBot 拼命令、轮询状态；服务依赖手动启动，功能限于只读可见性验证。

用户不希望引入另一套完整界面、T3 整套后端或不必要的第三方云连接。任务不能因 GrokBot 或 MCP 连接关闭而丢失，网络重试不能造成重复执行；必须准确区分已受理、正在执行、等待输入、完成、失败和交接完成。此前出现过官方 Desktop 消息加载失败和会话被另一进程占用，说明共享持久记录不等于可以同时操纵会话。

用户最终还希望任务完成后主动回传 GrokBot，并按需要让 Codex、ChatGPT 访问同一任务服务。主动通知是否能唤醒 GrokBot 尚未验证，不能以 MCP 事件发出成功代替用户收到消息。

## Solution

分三阶段交付，共用本机任务后端与统一任务标识。

1. **GrokBot 插件与结果查询闭环。** 提供可在用户本机 GrokBot 配置的 stdio MCP 接入包，连接独立常驻的任务服务。GrokBot 通过结构化工具提交、等待、读取、取消和续接任务；用户可以处理审批，并在释放执行占用后打开官方 Desktop 的同一会话。第一阶段不以其他客户端或主动通知为前提。
2. **验证并按能力实现主动通知。** 查明当前 GrokBot 的受支持消息投递或唤醒方式，在单个测试会话验证任务完成后实际收到通知并作出响应。如果不存在受支持入口，交付具体证据和查询回退方案，明确记录“主动通知未实现”，不宣称主动通知通过。
3. **按需要增加 Codex、ChatGPT 入口。** 仅在确有使用需求且客户端能力验证后，复用同一个后端增加适配。普通 Codex 执行结果由桥直接收集，不要求 Codex 安装插件。新增客户端不另建任务数据库，也不自动开启任意客户端间消息投递。

## User Stories

1. As a GrokBot 用户, I want 配置一次本地插件后用自然语言派活, so that 不必反复复制终端命令。
2. As a GrokBot 用户, I want 插件检测实际运行电脑与本机桥是否可达, so that 云端或错误主机不会被误报为本机成功。
3. As a GrokBot 用户, I want 查看可用项目, so that 能把任务交给正确的工作目录。
4. As a GrokBot 用户, I want 指定项目、任务目标及允许的执行权限, so that Codex 在明确范围内完成工作。
5. As a GrokBot 用户, I want 提交后快速取得任务 ID, so that 长任务不占住一次工具调用。
6. As a GrokBot 用户, I want 重试提交仍得到原任务, so that 响应丢失不会导致重复修改文件。
7. As a GrokBot 用户, I want 同一去重键配不同任务内容时收到冲突, so that 不会把旧结果误认为新任务结果。
8. As a GrokBot 用户, I want 查询最近任务并定位原任务, so that 忘记任务 ID 后仍能继续工作。
9. As a GrokBot 用户, I want 查询真实执行状态与有意义的进度, so that 能知道任务是否运行、受阻或已结束。
10. As a GrokBot 用户, I want 有界等待并在超时后继续查询, so that 等待超时不会取消实际任务。
11. As a GrokBot 用户, I want 取得模型实际最终答复及相关产物位置, so that 能检查交付而不只看到 completed 标记。
12. As a GrokBot 用户, I want 查看完整结果时支持分页或游标, so that 长输出不会被静默截断。
13. As a GrokBot 用户, I want 关闭聊天或 MCP 连接后任务继续执行, so that 客户端生命周期不控制工作生命周期。
14. As a GrokBot 用户, I want 重新连接后查到既有任务, so that 不必重新派活。
15. As a GrokBot 用户, I want 取消指定任务并确认执行已停止, so that 不再需要的操作不会继续运行。
16. As a GrokBot 用户, I want 在原会话追加新一轮需求, so that Codex 能保留前轮上下文。
17. As a GrokBot 用户, I want 原会话被 Desktop 使用时得到明确占用提示, so that 不会出现双方抢占或偷偷 fork。
18. As a 用户, I want 看见待审批操作的内容、目标与请求标识, so that 能作出具体批准或拒绝决定。
19. As a 用户, I want 拒绝或过期的审批不再执行, so that 权限决定真正约束行为。
20. As a 用户, I want 普通问题和权限审批被明确区分, so that 日常回答不会被误当成授权。
21. As a 用户, I want 完成后在官方 Codex Desktop 打开同一会话的完整消息, so that 能在熟悉的界面审阅和接手。
22. As a 用户, I want 执行中选择交接时先中断并释放占用, so that Desktop 能正常继续工作。
23. As a 用户, I want 同一项目的写任务默认排队, so that 多个任务不会同时修改同一工作目录。
24. As a 用户, I want 不同项目的任务有明确并发上限, so that 本机资源不会被无界派活耗尽。
25. As a 用户, I want 服务登录启动且崩溃后可恢复, so that 不用一直开着终端。
26. As a 用户, I want 重启后明确知道哪些任务中断或执行结果未确定, so that 不会误信成功或自动重复执行。
27. As a 用户, I want 原有任务记录升级后保留, so that 仍能查询和打开此前的会话。
28. As a 用户, I want 桥默认只在本机通信且不新增遥测, so that 不会因派活功能增加不必要的数据外发。
29. As a 用户, I want 凭据不出现在工具参数、日志或回复中, so that 插件使用不要求泄露登录信息。
30. As a 用户, I want Codex 升级不兼容时得到明确提示, so that 服务不会继续制造无法打开的会话。
31. As a 用户, I want 真正收到任务完成、失败或待处理通知, so that 不必一直主动轮询。
32. As a 用户, I want 通知仅送往任务所属且已授权的 GrokBot 会话, so that 不会错发到其他聊天。
33. As a 用户, I want 通知失败可查询、可受控重试且不重复执行任务, so that 消息投递故障不会改变执行结果。
34. As a 用户, I want 平台无法主动唤醒时得到诚实说明和查询回退, so that 能依据真实能力安排工作。
35. As a Codex Desktop 用户, I want 按需通过插件查询共享任务或明确提交跨客户端请求, so that 不必维护另一套任务状态。
36. As a ChatGPT 用户, I want 按需以其支持的认证与传输访问同一服务, so that 能使用相同任务 ID 查询结果。
37. As a 用户, I want 新入口遵守原有权限和会话占用规则, so that 多客户端接入不会扩大授权或打乱任务状态。
38. As a 用户, I want 可停用插件和服务而保留官方 Codex 会话, so that 验证方案可撤回且历史工作不丢失。

## Implementation Decisions

### 模块与阶段

- 沿用本机桥和官方 app-server 协议客户端，增加薄 MCP 适配层、持久任务管理、常驻服务管理及审批通道。复用官方客户端提供的认证，不复制或回显登录令牌。
- MCP 进程只负责工具契约和请求转发；任务执行归独立后台服务所有。断开 MCP 不终止 worker。
- 初期沿用带本地认证的 loopback 通信，不监听公网。stdio stdout 只输出 MCP 协议；诊断不混入协议流。
- GrokBot “插件”指可验证安装/配置的接入包。以实际客户端支持的 Command MCP 或插件机制交付，不凭空假设插件市场、manifest 格式或一键安装 API。
- 不引入第三方完整界面、T3 后端和云中继；首版保留 CLI 作为诊断入口。
- macOS 使用用户 LaunchAgent 承载后台服务；记录启动、停止、日志位置和卸载办法。退出登录、休眠仍是可用性边界，不宣称全天在线。

### 工具与数据契约

- 第一阶段工具：`list_projects`、`submit_task`、`list_tasks`、`get_task`、`wait_task`、`cancel_task`、`resume_task`、`open_in_desktop`，以及读取待处理问题/审批和提交答复的受控工具。
- `submit_task` 接收已注册的 project ID、任务文本、稳定 request ID、可选标题和允许范围内的执行配置；立即返回 job ID 和状态。thread ID 在创建成功后补齐。
- `resume_task` 只对桥已登记且当前可获得执行权的原 thread 新增 turn，并返回新的 job ID；使用自己的去重键，不把续接实现成 fork。运行中 steer 不属于首版合同。
- 去重键按调用方身份和操作类型划分，绑定请求内容摘要。相同请求返回既有 job；同键不同内容返回结构化冲突。
- `get_task` 返回 job/thread/turn 标识、状态、时间、待处理请求摘要、错误与可恢复性、会话是否已释放、Desktop 链接及实际结果。长结果显式提供游标和截断信息。
- `wait_task` 有明确超时上限，返回当前状态和是否等待超时；超时不取消任务，也不产生新 turn。
- `cancel_task` 幂等；返回取消请求受理与实际已停止两个不同状态。未运行的任务直接取消，运行中的任务先走协议中断，确认退出或释放后才报告可交接。
- 用 SQLite 替代原型 JSON 任务状态，保存 job、幂等请求、project、thread/turn 映射、状态变更、待处理交互、结果及交接状态；第二阶段再引入独立通知投递记录。数据库迁移保留原型任务记录。
- 不承诺跨进程 exactly-once。创建请求已发送但 thread ID 未落库时，先标记待核对并尝试对账；证据不足时禁止自动重新创建。

### 执行、权限与交接

- 每个活动任务使用独立 app-server，完成/中断后清理进程并确认会话释放。正常结果先持久化，再完成清理；任务执行结果与会话释放状态分别记录。
- 当前已验证版本需要 `paginated` 历史；保留历史兼容回归，不能把实验字段当成跨版本稳定承诺。
- 同一 thread 同时只有一个执行方。桥不得窃取 Desktop 的锁、修改官方数据库绕开占用或以静默 fork 掩盖冲突。
- `open_in_desktop` 默认要求已释放。执行中的交接由明确取消/交接请求触发，不能单因查看链接而终止工作。
- 第一阶段扩展到已登记项目的受控写入；同一项目写任务默认串行，不同项目有限并发。保留只读模式，不把原型 `approvalPolicy: never` 直接当成生产执行策略。
- 审批通过 request ID 关联操作、任务和有效期；桥验证请求仍待处理及用户决定，重复回答幂等，过期或不匹配决定拒绝。普通模型生成文字不构成人类授权。
- 首先验证 GrokBot 能否以受支持方式呈现并绑定人类审批；若不能，暂停相关执行并使用明确的人类交互入口。不得默认提高权限来绕过客户端缺口。
- 服务崩溃后检查记录和进程归属，先对账再接新工作；无法证明可继续的活动任务标记中断或待核对，不盲目重放有副作用的 turn。
- 原型固定三分钟的总运行超时不沿用为长期任务默认；区分 RPC 超时、客户端等待超时、无响应和用户指定任务期限。

### 通知与其他入口

- 第二阶段先核查 GrokBot 当前受支持的目标会话身份、投递、授权、唤醒和确认机制。MCP notification、HTTP 200、桌面系统通知均不能单独证明 GrokBot 已收到并响应。
- 若能力成立，通知记录与任务记录分离，使用事件 ID 去重、有界重试，投递失败不改变任务最终状态也不重新执行任务。只发送完成、失败、待处理等有意义变化，不发送无变化心跳。
- 不假设平台提供 exactly-once 投递；没有接收去重能力时明确重复通知边界。
- 默认通知只含状态、简短结果和任务链接；完整记录按授权查询。聊天目标必须来自已验证绑定，不接受任务正文中的任意目的地。
- 第三阶段的 Codex 插件、ChatGPT 连接器复用相同任务契约和权限。ChatGPT 所需远程传输、认证和可达性单独验证；不能将本地 stdio 配置直接当作 ChatGPT 接入方案。
- Codex 自身不需要插件来汇报正常执行结果。只有主动查任务或跨客户端交互需求才新增入口。

## Testing Decisions

用户已确认主要验收边界：**GrokBot MCP 工具入口 → 本机任务服务 → 官方 app-server → 真实结果 → 官方 Desktop 同会话读取/接手**。主动通知单独以 GrokBot 实际收到并响应作为验收标准。

- 测试外部行为，不断言私有函数调用次数、内部数据结构或模块拆分。主要自动化套件从真实 MCP 进程的 initialize/tools list/tools call 进入；复用同一套任务场景验证薄适配层和后台服务。
- 对故障注入，仅在既有 app-server 进程/JSON-RPC 边界替换可控测试进程，复现迟到响应、创建响应丢失、挂起、进程崩溃和重复事件。不为每个模块再造一套测试入口。
- 真实验收覆盖 GrokBot 发现工具、提交测试任务、读取实际答复、在官方 Desktop 看到同一 thread、释放后追加一轮成功。使用隔离测试项目验证受控文件写入和真实产物。
- 验证同一 request ID 重复提交只产生一个逻辑任务；同键不同内容报冲突；崩溃窗口不自动造成第二次有副作用执行。
- 关闭 MCP 客户端后任务继续，重新连接读取同一 job；停止后台服务则给出真实中断/待核对状态。服务重启与客户端断线分开测试。
- 验证 wait 超时不取消；取消后不继续执行；续接使用原 thread、新 turn；项目串行调度不同时写同一目录。
- 审批测试必须覆盖真实的人类批准、拒绝、超时/过期和重复答复。拒绝后不得发生受保护操作；普通问题答复不能批准权限请求。
- 桌面交接回归覆盖曾出现的消息加载失败和占用错误：分页读取成功、独立客户端获得原会话、桥进程释放、Desktop 显示实际正文并能继续。导航成功不等于验收通过。
- 先前已有独立客户端读取历史并 resume 的回归程序，以及 401 未认证、403 浏览器 Origin、400 无效输入和重复请求返回原任务的实测。将这些行为纳入 MCP/本机边界验收，不仅保留一次性运行记录。
- 第二阶段测试在 GrokBot 不主动轮询时完成任务，记录目标会话实际收到并响应的证据；还须验证错目标拒绝、断线后投递、重复事件、撤销绑定和投递失败查询。
- 第三阶段对每个新增入口重复同一套共享任务合同；其中一个客户端创建的 job 在另一个已授权客户端可查，权限和 thread 占用规则不变。
- 升级测试使用实际安装的官方二进制，记录版本和回归结果。没有兼容证据的版本不宣称支持；失败应给可操作错误。
- 本地检查和集成验收为默认，不新增 GitHub-hosted CI，不将真实凭据或私有会话放入测试夹具。

阶段完成标准：

| 阶段 | 必须具备的通过证据 |
|---|---|
| 第一阶段 | GrokBot 插件实际安装/配置并调用 MCP；真实派活与结果读取；取消、续接、审批及重连用例；Desktop 同会话正文与接手；常驻、重启及去重验证 |
| 第二阶段 | 受支持通知入口与目标绑定证据；GrokBot 无需主动查询而收到并响应；重试和去重边界明确。若能力不存在，提交可复查阻塞证据，主动通知保持未完成 |
| 第三阶段 | 对实际需要的客户端完成认证/传输互通与共享任务验收；没有需求的入口保留为后续范围，不为其阻塞前两阶段 |

## Out of Scope

- 重建完整桌面/Web 界面、看板、团队协作平台或多租户 SaaS。
- 引入 T3 全套后端、第三方遥测或默认云中继。
- 修改官方 Desktop 安装包、直接写官方会话数据库、全局 daemon 开关或绕过会话锁。
- 首版中桥与 Desktop 同时控制同一活动会话、运行中实时同步/steer，以及同项目并行 worktree 调度。
- 自动放行所有审批、默认全盘访问、无授权读取任意项目或跨客户端自动发消息。
- 第一阶段的公网入口、ChatGPT 远程 OAuth、多机器部署或移动端访问。
- 保证模型输出正确、断电后无损继续活动 turn、跨第三方消息系统 exactly-once。
- 在没有受支持接口证据时，以 UI 点击、私有接口注入或写入聊天存储伪造 GrokBot 主动通知。
- 本轮 to-spec 不包含实际开发、插件安装、服务安装或配置凭据；这些属于工单实施阶段。

## Further Notes

- 已验证事实：官方 Desktop 内置 Codex `0.162.0-alpha.2`；原型 V1 的 legacy 历史和会话占用导致用户可见错误；V2 使用 paginated 历史、退出任务进程后，独立读取/resume 及官方 Desktop 正文显示通过，用户回传 `BRIDGE_DESKTOP_OK_V2`。用户随后明确确认 GrokBot 派活验证通过。
- 尚未实现：MCP 插件、SQLite、常驻服务安装、生产执行权限/审批、取消/续接工具、主动通知、Codex/ChatGPT 新入口。不能把原型验证当成这些功能已完成。
- 隐私边界：本机中间层不等于离线模型。任务及上下文仍由 Codex 发给其模型服务；交给 GrokBot 的结果也进入 GrokBot。只传必要内容，不输出凭据。
